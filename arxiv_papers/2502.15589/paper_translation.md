## 摘要

大型语言模型（LLMs）在复杂推理任务中表现出色，但其效率受到生成大量 token 所带来的巨大内存和计算成本的影响。本文提出 **LightThinker**，一种使 LLM 能够在推理过程中动态压缩中间思维的新方法。受人类认知过程的启发，LightThinker 将冗长的思维步骤压缩为紧凑的表示形式，并丢弃原始推理链，从而显著减少上下文窗口中存储的 token 数量。这是通过以下方式实现的：在数据构建中训练模型何时以及如何执行压缩，将隐藏状态映射到浓缩的 gist token，并创建专门的注意力掩码。此外，我们引入 **Dependency (Dep)** 指标，通过测量生成过程中对历史 token 的依赖程度来量化压缩程度。在四个数据集和两个模型上的大量实验表明，LightThinker 在保持竞争力的准确率的同时，降低了峰值内存使用和推理时间。我们的工作为在不牺牲性能的情况下提高 LLM 复杂推理任务效率提供了新方向。

## 1. 引言

![图1：CoT 案例与 Vanilla 和 LightThinker 推理对比](figures/intro-v1.pdf)

**图1**：(a) 一个 CoT 案例。黄色高亮的 token 代表关键推理 token，其余 token 主要确保语言流畅性。人类在解决这个问题时通常只写黄色部分。(b) Vanilla 与 LightThinker 推理的对比。"C Ti" 表示第 i 个压缩后的思维表示，我们展示了压缩后可能表达的语义信息。

近年来，大型语言模型（LLMs）在复杂推理任务中展现出卓越的能力。随着该领域研究的进展，模型的推理模式逐渐从"快思考"演变为"慢思考"。这一转变以思维链（Chain-of-Thought, CoT）提示为代表，通过将复杂问题分解为多个子步骤并依次解决来增强模型的推理能力。在此基础上，**o1-like 思考模式**引入了试错、回溯、修正和迭代等多种推理能力，进一步提高了模型解决复杂问题的成功率。然而，这种性能提升是以生成大量 token 为代价的。

鉴于当前的 LLM 主要基于 Transformer 架构，注意力机制的计算复杂度随上下文长度呈二次方增长，而 KV Cache 的存储开销随上下文长度线性增长。例如，对于 Qwen32B 模型，当上下文长度达到 $10^4$ 时，KV Cache 占用的空间与模型本身相当。因此，token 生成的增加导致内存开销和计算成本急剧上升，严重限制了 LLM 在长文本生成和复杂推理任务中的实际效率。

为缓解这一问题，研究者提出了两类主要方法：

1. **无需推理干预的方法**：通过提示工程或专门训练引导 LLM 在推理过程中生成更少甚至零个中间 token
2. **实时 token 级干预的方法**：在推理过程中通过逐 token 干预，选择性保留 KV Cache 的重要部分

然而，这两种方法都面临挑战：前者通常需要仔细的数据构建和迭代优化，后者由于逐 token 重要性评估的计算开销而引入大量推理延迟。

在本工作中，我们提出了一种新方法：**训练 LLM 在推理过程中动态压缩历史内容**。我们的动机来自两个观察：

1. LLM 生成的 token 具有双重目的：确保语言流畅性和促进实际推理（如图1(a)黄色高亮部分所示），这使得压缩成为可能
2. 当人类解决类似图1(a)中的问题时，通常只写下关键步骤（黄色高亮部分），而将思维过程的其余部分存储在大脑中

基于这些见解，我们引入 **LightThinker**，一种在生成过程中动态压缩中间思维的方法。如图1(b)所示，在生成一个冗长的思维步骤（例如 Thought i）后，将其压缩为紧凑的表示（例如 C Ti），并丢弃原始思维链，仅基于压缩内容继续推理。这种方法显著减少了上下文窗口中存储的 token 数量，从而降低了内存开销和计算成本。

在实践中，我们训练 LLM 学习**何时压缩**和**如何压缩**。具体而言，我们构建数据来教导模型何时进行压缩；将待压缩思维的隐藏状态减少为对应于少量特殊 token（即 gist token）的隐藏状态集合。通过精心设计的注意力掩码，LLM 随后学习如何压缩以及如何基于压缩内容继续生成。

为量化推理过程中使用的信息量，我们进一步提出 **Dependency (Dep)** 指标，定义为每个生成 token 依赖的历史 token 总数（见图2）。该指标有效衡量压缩程度，较低的 Dep 值表示对原始长上下文的依赖减少，压缩效果更显著。

我们在四个数据集上使用两个不同模型进行了大量实验。结果表明，使用 Qwen 模型时，与 Vanilla 模型相比，LightThinker 减少了 **70%** 的峰值 token 使用量，降低了 **26%** 的推理时间，同时保持了可比较的准确率（仅下降 1%）。

## 2. 背景

### 慢思考

LLM 的推理能力至关重要，尤其是在解决复杂问题时，需要从快思考的系统1转向慢思考的系统2。例如，思维链（CoT）方法将复杂问题分解为子问题并逐步解决。**o1-like 思考模式**更进一步，在分治策略的基础上加入了试错、反思、回溯和修正等能力。实证证据表明，与 CoT 相比，o1-like 思考模式显著增强了模型解决复杂问题的能力。这种慢思考模式可以通过监督微调（SFT）使用精心构建的数据注入模型。就输出 token 数量而言，系统1、CoT 和 o1-like 思考模式的 token 消耗依次增加。

### 推理挑战

o1-like 思考模式的近期研究强调了解决复杂问题需要生成大量 token。作为 Transformer 的核心结构，注意力机制在推理过程中随着 token 生成规模的扩大面临两个重大挑战：

1. **内存开销**逐渐增加。为加速推理，每层都会缓存每个 token 的 Key 和 Value。对于 Qwen-32B，当上下文长度达到 $10^4$ token 时，KV Cache 占用的空间与模型本身相当。

2. **计算成本**：以自回归方式生成单个 token 的计算成本也增加。由于 Transformer 中的注意力机制，计算负载随 token 数量呈**二次方**增长。

## 3. 方法论

![图2：LightThinker 概览，以需要三步推理的例子说明](figures/method-v6.pdf)

**图2**：LightThinker 概览，以需要三步推理的例子说明。(a) 显示 Vanilla 在训练和推理期间的注意力掩码。(b) 描述 LightThinker 在训练期间的注意力掩码。(c) 展示 LightThinker 的完整推理过程及每一步对应的注意力掩码。`w` 表示矩阵的大小。

我们提出 **LightThinker** 来加速 LLM 的推理过程，如图2所示。核心思想是**训练 LLM 在推理过程中动态压缩当前思维**，使后续生成能够基于压缩内容而非原始长思维进行。

### 3.1 概述

**符号定义**。为清晰起见，我们定义以下符号。小写字母（如 $x_i$）表示单个 token。大写字母（如 $X$）表示 token 序列。符号 `\texttt{[·]}` 表示特殊 token（如 `\texttt{[c]}`），而 `\texttt{<·>}` 表示可选特殊 token（如 `\texttt{<w>}`）。o1-like 思考模式数据集 $\mathcal{D}=\{(X,Y)_i\}_{i=1}^{|\mathcal{D}|}$ 包含 $|\mathcal{D}|$ 个样本，其中 $X=\{x_i\}_{i=1}^{|X|}$ 表示问题，$Y=\{y_i\}_{i=1}^{|Y|}$ 表示对应的思维和最终答案。近期研究表明，在 $\mathcal{D}$ 上进行 SFT 显著增强了 LLM 的推理能力。

**设计**。为实现这一核心思想，我们重点解决两个关键问题：

**i) 何时压缩？** 压缩的时机显著影响推理效率和压缩质量。我们探索了两种不同策略：
- **token 级**：在固定数量的 token 后进行压缩。这种策略实现简单但可能忽略语义边界。
- **思维级**：在完整的"思维"（定义为句子或段落）后进行压缩。这种策略更好地保留语义信息但需要更复杂的分割函数。

**ii) 如何压缩？** 压缩的目标是将当前冗长的思维编码为更紧凑的表示。我们研究了两种不同方法：
- **文本压缩**：将当前思维编码为更短的文本或连续向量块。这种方法需要额外的编码模型并增加计算开销。
- **隐藏状态压缩**：将当前思维的隐藏状态压缩为少量特殊 token（即 **gist token**）的隐藏状态。我们选择这种方法，因为它不需要额外的模型。

在我们的工作中，我们通过**重构数据**解决第一个问题，通过**构建基于思维的注意力掩码**解决第二个问题。

**什么内容被压缩了？** 我们的目标不是将冗长的思维信息无损地压缩为紧凑表示。相反，我们专注于仅保留对后续推理至关重要的信息。如图1(b)中灰色虚线框所示，仅保留对进一步推断有显著贡献的元素。

### 3.2 LightThinker

**数据重构**。为使 LLM 能够在生成过程中动态压缩，我们按以下方式重构原始数据集 $\mathcal{D}$：

首先，我们分割输出。给定输入 $X$ 和输出 $Y$，我们使用分割函数 $\texttt{Seg()}$ 将 $Y$ 分割为 $k$ 个子序列 $S$，即 $Y=\{S_i\}_{i=1}^{k}$。该函数可以基于 token 级或思维级。

然后，我们插入特殊 token。具体而言，我们在相邻子序列 $S_i$ 之间插入一组特殊 token $\{\texttt{<w>}, C, \texttt{[o]}\}$，其中 $\texttt{<w>}$ 是可选的压缩触发器，表示需要压缩前面的思维。如果 $\texttt{Seg()}$ 是 token 级或 $\texttt{<w>} \in S_i$，则可以省略。token $C=\{\texttt{[c}_\texttt{i}\texttt{]}\}_{i=1}^{|C|}$ 由 $|C|$ 个特殊 token 组成，作为 gist token 存储压缩内容。这里我们将 $C$ 称为**缓存 token**，将 $|C|$ 称为**缓存大小**。token $\texttt{[o]}$ 是强制输出 token，使基于压缩内容的持续生成成为可能。

最终，增强后的数据为：

$$
\hat{Y}=\{S_1, \underline{\texttt{<w>}, C, \texttt{[o]}}, S_2, \underline{\texttt{<w>}, C, \texttt{[o]}}, \dots, S_k\},
$$

增强后的数据集定义为 $\hat{\mathcal{D}}=\{(X,\hat{Y})_i\}_{i=1}^{|\hat{\mathcal{D}}|}$。

**基于思维的注意力掩码构建**。为使 LLM 学习如何压缩以及如何基于压缩内容生成（即如何理解压缩内容），我们操纵**基于思维的掩码构建**，如图2(b)所示。

具体而言，令 $S_{\lt i}=\{S_1,\dots,S_{i-1}\}$ 表示第 $i$ 个思维 $S_i$ 之前的序列。

在压缩期间，$C^{(i)}$ token 只能关注问题 $X$、先前压缩的内容 $\{\{C,\texttt{[o]}\}^{(\lt i)}\}$ 和当前思维 $S_i$，即：

$$
\begin{aligned*}
C^{(i)} \leftarrow \texttt{Cmp}(X, \{C^{(1)}, \texttt{[o]}^{(1)}, \dots, C^{(i-1)}, \texttt{[o]}^{(i-1)}\}, S_i),
\end{aligned*}
$$

其中 $\texttt{Cmp()}$ 是压缩操作。这使 LLM 能够将 $S_i$ 的关键内容压缩到 $C^{(i)}$ 中。

在生成期间，token $\texttt{[o]}^{(i)}$ 只能关注问题 $X$ 和先前压缩的内容 $\{C, \texttt{[o]}\}^{(\le i)}$，即：

$$
\begin{aligned*}
S_{i+1} \leftarrow \texttt{Gen}(X, \{C^{(1)}, \texttt{[o]}^{(1)},\dots,C^{(i)},\texttt{[o]}^{(i)}\}),
\end{aligned*}
$$

其中 $\texttt{Gen()}$ 是生成操作。这使 LLM 能够基于问题和先前压缩的内容继续推理。

**训练与推理**。训练目标是最大化以下概率分布：

$$
\begin{aligned*}
&P_\theta(S_1|X) \cdot P_\theta (S_2|X,C^{(1)},\texttt{[o]}^{(1)})\cdot \dots \\
&\quad\cdot P_\theta ( S_k|X, \{ C^{(i)},\texttt{[o]}^{(i)} \}_{i=1}^{k-1}  ),
\end{aligned*}
$$

其中 $\theta$ 表示 LLM 参数。值得注意的是，在训练期间，LLM 不被允许预测输入 $X$ 和特殊 token $C$ 和 $\texttt{[o]}$。训练样本从 $\mathcal{\hat{D}}$ 中抽取，我们使用注意力掩码来鼓励 LLM 学习压缩和理解压缩内容。整个训练过程仍基于下一个 token 预测。详细的推理过程如图1(b)和图2(c)所示。

## 4. 实验

### 4.1 实验设置

**基线方法**。我们在两个 LLM 上进行实验：Qwen2.5-7B 和 Llama3.1-8B。为建立性能上限，我们使用 Bespoke-Stratos-17k 数据集（简称 B17K）进行全参数指令微调，微调后的模型记为 **Vanilla**。我们初始化训练时使用 R1-Distill 模型，因为我们发现基于指令模型的微调改进有限。

我们引入五个基线进行比较：
- 两个无需训练的加速方法应用于 Vanilla（H2O 和 SepLLM，通过特定策略保留重要 KV Cache）
- 一个基于训练的方法（AnLLM）
- 两个 CoT 基线（提示指令模型和 R1-Distill 模型）

**评估指标和数据集**。我们在四个数据集上评估 LightThinker：GSM8K、MMLU、GPQA 和 BBH。评估关注**有效性**和**效率**两个方面：
- 有效性：使用准确率（Acc）作为评估指标
- 效率：采用三个指标：推理时间（Time）、推理期间上下文中峰值 token 数量（Peak）、生成过程中每个生成 token 对先前 token 的依赖总和（Dep）

**实现**。对于 LightThinker，我们设计了两种不同的分割函数 $\texttt{Seg()}$：
- **token 级**：每 6 个 token 压缩为 2 个 token，即 $|C|=2$，记为 "ours (token)"
- **思维级**：使用 "{\textbackslash n\textbackslash n}" 作为分隔符将 B17K 数据简单分割为多个思维，记为 "ours (tho.)"

对于 Qwen，我们将一个思维压缩为 9 个 token（$|C|=9$）；对于 Llama，压缩为 7 个 token（$|C|=7$）。所有实验使用贪婪解码，最大输出长度为 10240 token。

2. H2O 在保持 Vanilla 性能的同时有效降低内存使用，表明贪婪淘汰策略在长文本生成任务中有效。然而，与 Vanilla 相比，H2O 显著增加推理时间，在 Qwen 上平均增加 51%，在 Llama 上增加 72%。这归因于 H2O 的逐 token 淘汰策略，为每个生成的 token 引入额外开销。

3. SepLLM 在性能方面表现最差，在生成过程中逐渐失去语言能力，导致无法输出终止 token，从而产生过多的推理时间。

4. 与 H2O 相比，LightThinker (tho.) 在相似的 Dep 值（即相似压缩率）下实现相似性能，同时在 Qwen 上平均减少 52% 的推理时间，在 Llama 上减少 41%。此外，与 AnLLM 相比，LightThinker (tho.) 保持更高的准确率和更快的推理速度。

**基于这些观察，我们得出以下结论**：

1. **B17K 是一个有效的数据集**。我们发现 Vanilla 在大多数数据集上优于 CoT 和 Distill-R1，表明 B17K 是一个有效的数据集，通过 SFT 缓解了 Distill-R1 中的重复问题。

2. **LightThinker 是有效的，在推理的有效性和效率之间取得了良好的平衡**。具体而言，在 Qwen 上，LightThinker 牺牲 1% 的准确率但节省 26% 的时间，减少 70% 的峰值 token，降低 78% 的 Dep（即实现 16.6/3.7=4.5x 压缩比）。在 Llama 上，它牺牲 6% 的准确率但节省 1% 的推理时间，减少 70% 的峰值 token，降低 74% 的 Dep（即实现 10.5/2.7=3.9x 压缩比）。

3. **分割函数对 LightThinker 至关重要**。思维级分割函数优于 token 级，在 Qwen 上准确率提高 6.2%，在 Llama 上提高 5.6%。这表明 token 级分割导致语义边界丢失。

## 5. 相关工作

当前加速 LLM 推理过程的研究主要集中在三类方法：**模型量化**、**生成更少 Token** 和**减少 KV Cache**。

模型量化包括参数量化和 KV Cache 量化。值得注意的是，生成长文本和理解长文本代表不同的场景；因此，这里不讨论专门针对长文本生成阶段的加速方法（如预填充阶段加速技术）。

### 减少 KV Cache

这类方法可以分为两种策略：离散空间中的基于剪枝的 KV Cache 选择和连续空间中的基于合并的 KV Cache 压缩。

1. **基于剪枝的策略**：设计特定的淘汰策略在推理期间保留重要 token。例如，StreamingLLM 将初始 sink token 和最近的 token 视为重要。H2O 关注具有 high 历史注意力分数的 token。SepLLM 强调对应于标点符号的 token。

2. **基于合并的策略**：引入锚点 token，并训练 LLM 将历史重要信息压缩到这些 token 中，从而实现 KV Cache 合并。

两种策略都需要在推理期间进行干预。关键区别在于第一种策略无需训练但为每个生成的 token 应用淘汰策略，而第二种是基于训练的方法，允许 LLM 决定何时应用淘汰策略。

## 6. 结论

在本文中，我们提出了 LightThinker，一种通过在生成过程中动态压缩中间思维来增强 LLM 复杂推理任务效率的新方法。通过训练 LLM 学习何时以及如何将冗长的思维步骤压缩为紧凑表示，LightThinker 在保持竞争力准确率的同时显著降低了内存开销和计算成本。我们引入 **Dependency**（简称 Dep）指标来量化不同加速方法的压缩程度和推理过程中使用的信息量。大量实验表明，LightThinker 是平衡效率和性能的有效方法。

---

## 局限性

尽管 LightThinker 在内存优化和推理速度提升方面取得了显著进展，但某些局限性值得仔细考虑：

1. **缓存 token 数量固定**：缓存 token 的数量在训练期间固定，在推理期间必须保持一致。这些 token 表示的泛化能力不确定。例如，用 3 个 token 训练的表示能否外推到推理期间需要更多 token 的场景。

2. **分割函数设计简单**：分割函数的设计相对简单，依赖于基于规则的方法。未来工作可以研究更先进的分割策略。

3. **未评估的任务**：LightThinker 在小说生成、代码生成和多轮对话等任务上的性能尚未评估。

## 附录：Dependency 指标详解

![图5：Dependency 指标说明](figures/metric-cal-v1.pdf)

**图5**：Dependency 指标说明。

### 动机

LightThinker 和 AnLLM 是动态压缩方法，意味着压缩次数和压缩比由 LLM 自身决定，而非预定义的超参数。相比之下，H2O 和 SepLLM 允许用户设置超参数来控制推理期间保留的最大 token 数量。这种根本差异使得难以直接和公平地比较像 LightThinker 和 AnLLM 这样的动态压缩方法与像 H2O 和 SepLLM 这样的 KV Cache 压缩方法。

传统上，KV Cache 压缩方法通过设置相同的最大峰值 token 数量进行比较，但在我们的背景下，这种指标变得不充分。如图5所示，虽然 LightThinker 偶尔在峰值 token 数量上超过 H2O，但这个指标具有误导性，因为 LightThinker 的峰值内存使用仅瞬间发生，而 H2O 随时间保持 consistently high 的 token 数量。

### 定义

我们引入 **Dependency**（简称 Dep）指标，定义为生成输出期间每个生成 token 对先前 token 的依赖总和。几何上，它表示图5中曲线下的面积。

**Vanilla 的 Dependency**：

$$
\begin{aligned*}
\texttt{Dependency} &= \frac{(L_P + L_P + L_O) \times L_O}{2} \\
&= \frac{{L_O}^2}{2} + L_P \times L_O
\end{aligned*}
$$

**H2O 的 Dependency**：

$$
\begin{aligned*}
S_\texttt{Trapezoid} &= \frac{(L_P + L_C) \times (L_C - L_P)}{2} \\
S_\texttt{rectangle} &= L_C \times (L_O - L_C + L_P) \\
\texttt{Dependency} &= S_\texttt{Trapezoid} + S_\texttt{rectangle} \\
&= \frac{2L_PL_C + 2L_OL_C - {L_P}^2 - {L_C}^2}{2}
\end{aligned*}
$$

**LightThinker 和 AnLLM 的 Dependency**：

对于 LightThinker 和 AnLLM，Dependency 没有闭式解，必须根据其定义迭代计算。

### 应用

**Dependency 的价值**：较高的 Dependency 值表示生成期间需要考虑更多 token，反映使用更多信息。相反，较低的 Dependency 值表示更高的有效压缩比。

**Dependency 比率**：通过将加速方法的 Dependency 除以 Vanilla 的 Dependency，我们获得相对于 Vanilla 的压缩比。例如，在表1的 "Avg." 列中，Vanilla 的 Dependency 为 16.6M，H2O 为 4.4M，LightThinker 为 3.7M。因此，H2O 实现 $16.6/4.4 \approx 3.8$ 的压缩比，而 LightThinker 实现 $16.6/3.7 \approx 4.5$ 的压缩比。

该指标为评估动态和静态压缩方法提供了统一框架，确保公平和有意义的比较。

AnLLM 是一种与我们的方法相关的方法。在图6中，我们比较了 LightThinker 和 AnLLM 在注意力掩码上的差异：

## 附录：从其他视角看 LightThinker

在之前章节中，我们从压缩角度设计了 LightThinker。这里，我们进一步从**内存**和**KV Cache 压缩**角度讨论它，其中 KV Cache 可被视为 LLM 工作内存的一种形式。

**内存视角**：LightThinker 的工作流程可以总结如下：首先进行自回归推理，然后将推理过程中的关键信息存储为内存，并基于记忆内容继续推理。因此，缓存 token 中的信息充当紧凑内存，尽管它仅对当前 LLM 有效且缺乏可迁移性。

**KV Cache 压缩视角**：与 H2O 等方法依赖手动设计的淘汰策略选择重要 token 不同，LightThinker 在连续空间中合并先前的 token，**创建**新的表示。合并的内容和方式由 LLM 自主决定，而非离散选择过程。
